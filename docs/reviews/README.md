# docs/reviews —— 定期评审

**这里放的是"某一天的判断"，不是事实。** 与别处的分工：

| 想知道 | 去哪 |
|---|---|
| 今天的代码长什么样 | [`../current/`](../current/) |
| 某个设计为什么这样定 | [`../adr/`](../adr/) |
| 在建的施工计划 | [`../plans/`](../plans/) |
| 某一天的评审结论 | 就是这里 |

一份评审落地之后，把它产出的**事实**搬进 `current/`、**稳定决策**写成 ADR，然后这份评审
就只剩考古价值 —— 不要留在原地当"半个事实源"（同 [`../plans/README.md`](../plans/README.md)
的约定）。评审里的结论被推翻时**不删**：在文件顶部记一行去向。

## 两份评审的分工

`2026-09-05` 修的是"执行语义对不对"——一次 Run 会不会丢任务、终态会不会被覆盖、压缩会不会
串分支。那份的结论已经进代码，当前事实读 [`../current/run-lifecycle.md`](../current/run-lifecycle.md)。

`2026-10-10` 评的是"能力够不够"——没有评测所以无法判断 agent 干得对不对、bash 无沙箱、
模型调用层没有自己的重试与超时、token 估算在中文下失真。**它不复述前者已修的部分**，
只标注哪几条**仍未闭环**（真 provider 的 agent 质量任务集、外部 MCP 副作用、强杀恢复、
长时 soak —— `2026-09-05-refactor-progress.md` 的 *Remaining release validation* 五条里，
`2026-10-10` 认为其中三条是同一个根因：缺评测）。

## 写新评审的三条约定

1. **结论要带证据等级。** 每条都要能回答"我是读出来的、跑出来的，还是推出来的"。
   动态复现的写清复现方式；静态阅读的明说没跑过。
2. **区分"事实"与"判断"。** "有 88 个测试文件"是事实；"评测该先做"是判断。
   判断可以错，所以要把依据写出来，方便后来的人推翻它。
3. **不要复述已归档评审的内容。** 指向它，只写增量。
